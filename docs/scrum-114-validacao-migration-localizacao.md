# SCRUM-114 — Validação da migração V1 de localizações

A [V1](../src/main/resources/db/migration/V1__create_table_localizacao.sql) foi aplicada diretamente em dois bancos vazios e descartáveis: **H2 2.4.240** em memória, no dialeto padrão, e **PostgreSQL 17.12**, em um contêiner temporário da imagem `postgres:17` sem portas publicadas. As duas execuções criaram a tabela e o índice `idx_localizacao_local_pai_id`. O contêiner foi removido ao final.

## Estrutura e resultados

| Verificação | Correspondência na aplicação | H2 2.4.240 | PostgreSQL 17.12 |
| --- | --- | --- | --- |
| `id BIGINT GENERATED BY DEFAULT AS IDENTITY` | `Long id` com `GenerationType.IDENTITY` | Gerou IDs 1, 2 e 3 | Gerou IDs 1, 2 e 3 |
| Chave primária de `id` | `@Id` | Rejeitou ID repetido com `23505` | Rejeitou ID repetido com `23505` |
| `uk_localizacao_codigo` | `@Column(unique = true)` em `codigo` | Rejeitou código repetido com `23505` | Rejeitou código repetido com `23505` |
| `fk_localizacao_local_pai` | `@ManyToOne` com `@JoinColumn(name = "local_pai_id")` | Aceitou raiz sem pai e filha ligada à raiz. Rejeitou pai inexistente com `23506` | Aceitou raiz sem pai e filha ligada à raiz. Rejeitou pai inexistente com `23503` |
| `chk_localizacao_local_pai_diferente_id` | `Localizacao.validarHierarquia()` rejeita autorreferência direta e também verifica ciclos indiretos | Rejeitou a autorreferência na atualização da filha com `23513` | Rejeitou a autorreferência na atualização da filha com `23514` |
| `NOT NULL` em `codigo` e `nome` | `nullable = false` na entidade e `@NotBlank` no DTO | Rejeitou ausência de cada campo com `23502` | Rejeitou ausência de cada campo com `23502` |
| `VARCHAR(50/255/100/255)` | Limites do DTO para `codigo`, `nome`, `tipo` e `descricao`; o limite de `nome` no mapeamento JPA é o padrão de 255 | Aceitou valores no limite e rejeitou cada excesso com `22001` | Aceitou valores no limite e rejeitou cada excesso com `22001` |

A consulta final nos dois bancos retornou apenas os três registros válidos. A filha manteve o ID 1 como pai após a tentativa de autorreferência. O `CHECK` da V1 cobre a autorreferência direta. A inspeção de ciclos indiretos pertence à validação da entidade.

## Roteiro manual

Em um banco vazio e descartável, execute a V1 e depois o SQL abaixo. Execute cada comando separadamente ou use o cliente em modo autocommit para continuar após as rejeições esperadas. Os dois `SELECT` devem mostrar três registros e os comprimentos `50, 255, 100, 255`.

```sql
INSERT INTO localizacao (codigo,nome) VALUES ('114-RAIZ','Raiz ficticia');
INSERT INTO localizacao (codigo,nome,local_pai_id) SELECT '114-FILHA','Filha ficticia',id FROM localizacao WHERE codigo='114-RAIZ';
INSERT INTO localizacao (codigo,nome,tipo,descricao) VALUES (repeat('C',50), repeat('N',255), repeat('T',100), repeat('D',255));
INSERT INTO localizacao (id,codigo,nome) SELECT id,'114-PK','PK duplicada' FROM localizacao WHERE codigo='114-RAIZ';
INSERT INTO localizacao (codigo,nome) VALUES ('114-RAIZ','Codigo duplicado');
INSERT INTO localizacao (codigo,nome,local_pai_id) VALUES ('114-ORFA','Pai inexistente',999999);
UPDATE localizacao SET local_pai_id=id WHERE codigo='114-FILHA';
INSERT INTO localizacao (codigo,nome) VALUES (repeat('C',51),'Codigo longo');
INSERT INTO localizacao (codigo,nome) VALUES ('114-NOME-LONGO',repeat('N',256));
INSERT INTO localizacao (codigo,nome,tipo) VALUES ('114-TIPO-LONGO','Tipo longo',repeat('T',101));
INSERT INTO localizacao (codigo,nome,descricao) VALUES ('114-DESC-LONGA','Descricao longa',repeat('D',256));
INSERT INTO localizacao (nome) VALUES ('Sem codigo');
INSERT INTO localizacao (codigo) VALUES ('114-SEM-NOME');
SELECT id,codigo,local_pai_id FROM localizacao ORDER BY id;
SELECT char_length(codigo) AS codigo, char_length(nome) AS nome, char_length(tipo) AS tipo, char_length(descricao) AS descricao FROM localizacao WHERE codigo=repeat('C',50);
```

## Avaliação dos alertas

O [workflow do projeto](../.github/workflows/migration-quality.yml) usa o SQLFluff em dialeto ANSI. O alerta de interpretação citado no [SCRUM-114](https://team-senai.atlassian.net/browse/SCRUM-114) é um falso positivo para os dois ambientes executados: ambos aceitaram o DDL e aplicaram as restrições. O log histórico do alerta não foi reproduzido localmente.

Os limites `VARCHAR` coincidem com o `@Size` do DTO e foram aplicados pelos dois bancos. Trocar para `TEXT` eliminaria essa proteção no banco. Os avisos do Squawk sobre locks são informativos para esta instalação em esquema vazio: a tabela, suas restrições e seu índice são criados na mesma migração. A execução não mediu bloqueios concorrentes em um ambiente compartilhado.

A evidência não indica necessidade de uma nova migração. A validação aplicou o SQL diretamente, sem testar o histórico do Flyway ou atualizar um banco existente.
